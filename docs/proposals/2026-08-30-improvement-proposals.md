## 1. Adopt `next/link` for internal navigation site-wide

**Idea:** Replace plain `<a href="/...">` internal links with `next/link`'s
`Link` component across `components/SiteHeader.tsx`,
`components/ContactSection.tsx`, `app/page.tsx`, `app/about/page.tsx`,
`app/services/page.tsx`, `app/itops-console/page.tsx`,
`app/network-topology/page.tsx`, `app/guides/page.tsx`, and the three guide
detail pages under `app/guides/*/page.tsx`.

**Rationale:** `app/demo/page.tsx` (lines 56 and 120) is the only place in
the app that imports and uses `next/link`'s `Link` — everywhere else uses a
raw `<a href="/...">`: `SiteHeader.tsx` (13, 30, 60),
`app/page.tsx` (43, 46, 91, 109), `app/about/page.tsx` (99, 102),
`app/services/page.tsx` (98), `app/itops-console/page.tsx`
(291, 304, 307, 310, 313, 578), `app/network-topology/page.tsx`
(161, 174, 177, 180, 183), `app/guides/page.tsx` (36-37), and each guide page's
"All guides" / contact CTA links — roughly 25 internal links against 2 that
use `Link`. That gap is more than stylistic: `Link` prefetches routes at rest
and swaps content client-side, while every other internal link forces a full
page reload/repaint — even though the header (`SiteHeader.tsx`), which
appears on nearly every route, is entirely un-migrated. `demo/page.tsx`
already shows the correct pattern in the same codebase; the rest of the app
just doesn't use it.

## 2. Keyboard/screen-reader access to the network topology SVG

**Idea:** Give the clickable site nodes in `app/network-topology/page.tsx`
(the `<g key={site.id} onClick={() => setSelectedSite(site.id)}>` elements,
lines 309-354) a `role="button"`, `tabIndex={0}`, an `onKeyDown` handler for
Enter/Space, and an `aria-label` naming the site and its status. Also add a
non-color status cue (icon or pattern) alongside `getStatusColor`
(lines 130-141), since an unselected node's status is currently conveyed by
fill color alone.

**Rationale:** The topology diagram is the site's demo centerpiece, and the
only way to inspect a site's bandwidth, latency, or device count is to click
its node and populate the details panel (`siteData`, lines 369-416). Those
nodes are plain SVG `<g>` elements with only an `onClick` and
`cursor: pointer` styling (lines 309, 329) — no `role`, no `tabIndex`, no
keyboard handler — so a keyboard-only or screen-reader user can never select
anything but the hardcoded default (`'hq'`, line 126) and never learns any
other site's metrics. The fix pattern already exists two hundred lines lower
in the same file: the "All Sites" list (line 424) correctly uses a real
`<button>` for the identical `setSelectedSite` action. The primary
interaction — the diagram itself — just doesn't use it.

## 3. Sitemap `lastModified` always equals build time, not the actual content-change date

**Idea:** In `app/sitemap.ts`, replace the per-entry `lastModified: new Date()`
calls with a fixed per-route date (or a date sourced from content metadata in
`lib/content.ts`, e.g. a `lastUpdated` field added to each guide) so `lastmod`
reflects when a page's content last actually changed.

**Rationale:** This is a static export (`output: 'export'`,
`next.config.mjs:3`) with `export const dynamic = "force-static"`
(`sitemap.ts:5`) — `sitemap.xml` is generated once per build and shipped as a
static file. Every entry — the 8 static routes (lines 18, 24, 30, 36, 44, 49,
55, 61) and every guide via `guideEntries` (line 10) — calls `new Date()`, so
every single route gets the identical `lastmod` timestamp: the moment that
particular build ran, regardless of whether that page's copy changed at all.
`lastmod` exists so crawlers can prioritize re-fetching recently-changed
pages; here it can't do that job, and a deploy that only touched, say,
`next.config.mjs` or a workflow file still stamps every page — home, guides,
demos — as "changed today," which search engines are documented to discount
once a sitemap's `lastmod` proves consistently unreliable.
