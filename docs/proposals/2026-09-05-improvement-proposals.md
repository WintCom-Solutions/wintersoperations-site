## 1. `.github/dependabot.yml`'s `pip` ecosystem entry is dead configuration

**Idea:** Remove the `package-ecosystem: pip` block
(`.github/dependabot.yml` lines 3-12) from this repo's Dependabot config, or
replace it with whatever ecosystem this repo actually needs Dependabot to
watch beyond `npm` and `github-actions` (which are both already configured
correctly below it).

**Rationale:** The block points `directory: "/"` at this repo's root for a
`pip` manifest, but there is no `requirements.txt`, `pyproject.toml`,
`Pipfile`, `setup.py`, or any other Python dependency manifest anywhere in
the tree — confirmed by searching the repo for `extension:py`, which returns
exactly one file: `.github/taskforce/grok_review.py`, a standalone review
script invoked by a workflow that calls `xai_sdk`/`openai`-style APIs
directly with no manifest of its own (no `pip install` appears anywhere in
`.github/workflows/` either). A `pip` Dependabot job with no manifest to
read has nothing to update — it runs weekly, finds no lockfile, and silently
produces nothing, forever. This is a small, low-risk config-drift item: it
doesn't break anything today, but it's misleading configuration that
implies a Python dependency surface this repo doesn't have, most plausibly
carried over unpruned from a different (Python) repo's Task Force
onboarding template.

## 2. The demo device-inventory search can never match by serial number

**Idea:** In `app/itops-console/page.tsx`, change line 101 from
`device.serialNumber.includes(normalizedQuery)` to
`device.serialNumber.toLowerCase().includes(normalizedQuery)`, matching the
pattern already used two lines above it for `model`/`site`/`siteAddress`.

**Rationale:** `searchDevice` (lines 82-115) builds `normalizedQuery` once,
always lower-cased and trimmed (line 90:
`query.toLowerCase().trim()`), then checks it against seven fields of the
one mock device (lines 94-101):

```ts
const isMatch =
  device.hostname.includes(normalizedQuery) ||
  device.ip.includes(normalizedQuery) ||
  device.mac.includes(normalizedQuery) ||
  device.model.toLowerCase().includes(normalizedQuery) ||
  device.site.toLowerCase().includes(normalizedQuery) ||
  device.siteAddress.toLowerCase().includes(normalizedQuery) ||
  device.serialNumber.includes(normalizedQuery);
```

`model`, `site`, and `siteAddress` are explicitly re-lowercased before the
comparison because their source values contain mixed case
(`'Cisco Meraki MS425-32'`, `'San Francisco Regional'`, etc.).
`hostname`/`ip`/`mac` skip that call but happen to work anyway because the
mock data for those three fields (`'switch-sf-01'`, `'192.168.1.10'`,
`'00:1a:2b:3c:4d:5e'`) is already all-lowercase. `serialNumber`, however, is
`'Q2QN-ABC4-DEFG'` — all uppercase letters — and is compared with `.includes`
directly against the always-lower-cased `normalizedQuery` with no
`.toLowerCase()` of its own. Since a lower-case string can never appear as a
substring of an all-uppercase one, **no input value, in any case, ever
matches by serial number** — not `Q2QN-ABC4-DEFG` (the exact string shown as
one of four example formats in the search input's own placeholder text), not
`q2qn-abc4-defg`, nothing containing a letter. Typing the serial number
exactly as the UI suggests always produces the page's "No device found
matching" message. This is the one page in the site built specifically to
demonstrate device-inventory search competence, and one of its four
advertised search fields is silently non-functional.

## 3. No structured data (JSON-LD) anywhere on the site

**Idea:** Add `Organization` (or `ProfessionalService`) JSON-LD structured
data — name, URL, logo, and contact point at minimum — to `app/layout.tsx`
(or a shared helper alongside `lib/metadata.ts`), and optionally per-page
`Service`/`Article` structured data for `/services` and the guide pages.

**Rationale:** A repo-wide search for `ld+json` and for `schema.org` both
return zero matches — there is no `<script type="application/ld+json">`
block anywhere in `app/` or `components/`. That's a real gap given how much
the rest of the SEO layer already invests in exactly this kind of
discoverability: `lib/metadata.ts`'s `createPageMetadata` sets a canonical
URL, full Open Graph, and Twitter card metadata for every route;
`app/sitemap.ts` and `app/robots.ts` exist specifically to help search
engines crawl the site correctly; and `scripts/verify-metadata.mjs` is a
purpose-built script, wired into `package.json`, that asserts on canonical
and OG tags in the built HTML. None of that infrastructure gives Google or
Bing anything to build a knowledge-panel entry, sitelinks search box, or
rich result from — structured data is the missing piece that would let a
search engine that already reads (and, per the existing scripts, verifies)
this page's OG/canonical tags also understand *what kind of business*
Winters Operations is, its logo, and how to contact it, directly from
markup rather than by inference.
