## 1. Wire the repo's own verification scripts and lint into CI

**Idea:** Add `npm run lint`, `npm run verify:metadata`, and
`npm run verify:contact` as steps in `.github/workflows/ci.yml`, alongside
the existing `npm ci` / `npm run build`.

**Rationale:** `package.json` already defines `verify:contact`
(`scripts/verify-contact.mjs`) and `verify:metadata`
(`scripts/verify-metadata.mjs`) — purpose-built checks for canonical URLs, OG
tags, and contact-form config across every route — plus a `lint` script, but
`ci.yml` only runs `npm ci` and `npm run build` today. A regression in
`lib/site.ts` or `lib/content.ts` that breaks a canonical tag or a Google
Form entry ID currently builds and merges cleanly with nothing catching it.
This is the highest-leverage, lowest-risk item of the three: no new tooling,
just wiring up checks the repo already wrote and is not running.

## 2. Fix the opaque `no-cors` contact-form submission path

**Idea:** In `components/ContactForm.tsx`, replace the `mode: "no-cors"`
fetch with a submission path that can actually distinguish success from
failure (a same-origin API route/proxy, or a provider response that isn't
opaque), and log a success/failure analytics event using the
`@vercel/analytics` integration already installed elsewhere in the app.

**Rationale:** `no-cors` mode (line 47) makes the response opaque, so a
server-side rejection — a bad Google Form entry ID, a Formspree quota hit —
is indistinguishable from success, and `setStatus("sent")` fires regardless.
For a business site where the contact form is a primary lead channel, a
silently-swallowed submission failure is a real business cost with no
visibility: nothing currently logs it, despite analytics already being wired
up in `app/layout.tsx`.

## 3. Add automated tests for the two large interactive dashboard pages

**Idea:** Add Jest or Vitest + React Testing Library and cover
`app/itops-console/page.tsx` and `app/network-topology/page.tsx` first —
the two most complex, stateful client components in the app.

**Rationale:** There is no `*.test.*`/`*.spec.*` file and no test-runner
config anywhere in the repo. Those two pages are 594 and 491 lines
respectively, with non-trivial `useState`/`useEffect`-driven interaction
(simulated device search, alerts), but the only existing automated checks
are the two Node scripts referenced in proposal #1, which assert on static
HTML output — not component behavior. A regression in either page's
interaction logic currently has no automated backstop at all.
